# Kairu Discord Bot Setup and Activation

**Document status:** This is a procedure to follow. It does not indicate that any command, environment, credential, or deployment currently exists.

## Preconditions

Complete this procedure first in a staging environment. The operator needs approved access to the Discord Developer Portal, the Kairu source repository, the central API configuration, Railway, the designated secret manager, and a backup/restore runbook. A bot token, provider secret, or `DATABASE_URL` must never be pasted into a ticket, shell history, committed file, or chat message.

| Gate | Required evidence before proceeding | Stop condition |
|---|---|---|
| Ownership | Named release, API, database, and Discord owners. | No person can approve a rollback or secret rotation. |
| Code | A reviewed, immutable commit or release artifact. | Unreviewed local changes or unpinned dependency drift. |
| API | Staging API base URL, `/health` result, and bot service credential configured. | Bot would call a placeholder, public mock, or direct database endpoint. |
| Database | Restore-tested staging backup and approved migration SQL. | No current backup or schema compatibility review. |
| Discord | Test guild and least-privilege install link prepared. | Production guild is the first test target. |
| Observability | Structured logs, error alert, uptime check, and audit correlation ID plan. | Failure cannot be detected or attributed. |

## Exact staging activation procedure

1. **Prepare configuration.** Obtain the approved values from the secret manager. Create a local untracked environment file only if local testing is approved. Populate it from the placeholder inventory in [Environment variables](ENVIRONMENT_VARIABLES.md). Confirm with `git status` that no `.env` file or secret-bearing export is staged.
2. **Install the locked dependency set.** Use the package manager and lockfile selected by the repository. A typical Node release uses `npm ci`; use `pnpm install --frozen-lockfile` only when the repository declares pnpm. Do not substitute a broad update command during an activation.
3. **Validate configuration without disclosing values.** Run the application’s configuration validation or a designated check command. Record only variable names and pass/fail status. A missing required secret is a failed preflight, not a reason to use a dummy production value.
4. **Generate the Prisma client mapping.** In this bot repository run `npm run prisma:format`, `npm run prisma:validate`, and `npm run prisma:generate`. These commands do not apply DDL. Never run `prisma migrate` or `prisma db push` from the bot.
5. **Apply reviewed control-plane SQL once.** The control-plane release job is the sole DDL authority. Apply its reviewed SQL against staging, not any migration generated by the bot.
6. **Verify schema compatibility from the control plane.** Confirm the control-plane SQL release/version and bot Prisma mapping agree. Do not hand-edit migration history or let the bot repair schema drift.
7. **Deploy the central API.** Confirm the API health endpoint succeeds, its release/version is expected, database connectivity is healthy, and it accepts the bot’s service authentication. The bot is not activated until this gate passes.
8. **Deploy the bot as its own service in dormant mode first.** Leave `DISCORD_TOKEN` absent and verify `/health` reports `gateway=dormant`. Then add the token only after the API, database schema, command-registration, least-privilege permissions, monitoring, and rollback gates are approved.
9. **Install in the staging guild.** Follow [Discord setup](DISCORD_SETUP.md), select the staging guild, and validate the permission screen. Confirm the bot appears online only if the chosen runtime uses a Gateway connection; HTTP interaction implementations may not need Gateway presence.
10. **Register and test commands.** Use the project’s controlled command-registration mechanism. Prefer guild-scoped commands for staging. Invoke `/setup-server`, then repeat it. Confirm one configuration record per guild and no duplicate Discord artifacts. See [Commands](COMMANDS.md).
11. **Test the failure paths.** Submit a request with an invalid HMAC, a duplicate event ID, an API authorization failure, and a simulated Discord 429 response. Confirm safe rejection, no canonical mutation, and useful redacted logs.
12. **Record the release decision.** Store commit ID, migration IDs, environment, time, approver, dashboard URLs, initial health result, and rollback deployment ID in the release record. Do not record secrets.

## Production activation procedure

Production activation repeats the staging procedure after a formal go/no-go decision. Before step 5, take or verify a current recoverable PostgreSQL backup. Before step 8, identify the most recent known-good API and bot deployments. After step 10, expose the bot to a small approved guild or a controlled feature flag before broad availability, when that rollout model is supported.

| Verification | Acceptance criterion | Operator action if it fails |
|---|---|---|
| Interaction acknowledgement | Discord interaction is acknowledged within the application’s designed response window. | Disable the new release or feature path; inspect latency and API reachability. |
| Canonical write | Exactly one API audit record and one expected state transition exist. | Stop retries that lack an idempotency key; inspect deduplication. |
| `/setup-server` replay | A second invocation returns the same configuration or an explicit no-change result. | Roll back the configuration change or reconcile manually under change control. |
| Webhook verification | Valid signature succeeds; invalid signature is rejected before parsing or side effects. | Rotate the affected secret if authenticity is uncertain; keep endpoint disabled. |
| Backups | Backup is current and restoration evidence exists. | Do not proceed to broad activation. |

## Prisma migration safety and rollback

A database rollback is not automatically provided by reverting application code. An additive migration can often be followed by a code rollback, but destructive data changes, type changes, or backfills can require a separately reviewed forward-fix or restore. Review lock risk, data loss, and compatibility before deployment; Prisma identifies heavy-lock patterns such as non-concurrent index creation and column type changes as migration risks. [1]

Use **expand–migrate–contract** for changes used by both API and bot. First add compatible columns or tables. Then release code that can read both forms and backfill in controlled batches. Only after all compatible callers are gone should a later release remove old fields. Do not start API and bot deployments that depend on incompatible schema assumptions at the same time.

| Situation | Safe first response | Database decision |
|---|---|---|
| Bot release fails before writes | Roll back bot deployment. | No migration reversal unless a migration actually ran. |
| API code regression after additive migration | Roll back API code to a version compatible with the expanded schema. | Leave additive schema in place. |
| Bad data migration or destructive change | Stop writers, preserve evidence, assess blast radius. | Use the approved forward repair or restore point; do not improvise SQL. |
| Migration partially applies | Stop release and capture Prisma output. | Follow Prisma production troubleshooting with database owner approval. |
